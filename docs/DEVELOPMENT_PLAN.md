# 酒醴（jiǔlǐ）开发计划

> **一句话定义**：一个开箱即用的本地角色扮演引擎——把酒馆角色卡无损蒸馏成结构化语义，
> 用瘦上下文运行时驱动"有记忆、有生活、成本可控"的角色扮演。
>
> **定位语**：比 RisuAI 多生命感，比酒馆少折腾，比托管平台自由。
>
> 代号「酒醴」为占位名，正式名后定。
> 本计划假设：1 名全职开发者 + AI 辅助编程；周期约 24 周到公测，阶段间可并行压缩。

---

## 0. 背景与依据（为什么做、凭什么是我们）

| 结论 | 来源 |
|---|---|
| 市场空位：低部署 × 酒馆级兼容 × agent 生命感，三轴交集无人占 | 竞品调研（RisuAI / ST / OpenCharaAgent / NekoBot / dsh-liketavern / 托管平台） |
| 最难的一环已有一半：卡片结构化解析（extract_card.py，700 行，字段覆盖全） | tavern-card-distiller 代码审查 |
| 三条代差：跨会话记忆、中文语义触发、校验闭环 + 硬数字（单轮 2-4K token，约酒馆重度配置 1/5 成本） | 产品定义 |
| skill 形态是入口/试玩版，不是产品本体（上下文主人是宿主，常驻能力缺失） | 架构分析 |

**不做清单（第一年）**：工具沙箱共创、桌面 App 全家桶、卡片市场、Card Studio、账号体系、托管服务。

## 2. 阶段详解

### P0（第 1-2 周）：地基修复与技术决策

**目标**：把现有资产修到可发布，用实验数据钉死两个关键决策。

任务清单：
1. 修复 `extract_card.py:704` f-string 语法错误（Python <3.12 直接 SyntaxError，本地 3.8 实测复现）
2. 修复 `generate_skill.py` 两个数据破坏点：
   - 下载脚本绝对路径（改为 `$(dirname "$0")` 相对路径，`generate_skill.py:242`）
   - 重装时 `rmtree` 删光 chat_history/user_profile（改为合并式覆盖，`generate_skill.py:1104`）
3. 清理硬编码：`_guess_character_from_scene` 的角色白名单；`#!/bin/zsh` 改 bash；README 补 LICENSE
4. **发布 tavern-card-distiller v0.2**（独立迁移工具，作为漏斗顶端）
5. **检索实验（本阶段最重要的产出）**：
   - 用 jieba 分词 + BM25（rank_bm25 或 tantivy-py）+ 本地中文 embedding（bge-m3）对 11 张卡的世界书做双通道召回实验
   - 自建 50 组"场景表述 → 应命中条目"标注（含中文改写：同义词/代词/场景描述）
   - 决定：embedding 本地跑 vs API、融合策略（RRF）、阈值策略
6. **Fork 评估（timebox 一周）**：跑通 OpenCharaAgent，读事件协议与 agent core，评估能否挂"确定性状态执行层"
   - 产出决策记录：fork 复用 vs 自建薄运行时（两者都预留撤退路径）

**产出**：v0.2 发布、检索实验报告、fork 决策记录、schema v0 草案。

### P1（第 3-5 周）：蒸馏层——从"生成散文"到"卡片语义包"

**目标**：蒸馏器的输出从 SKILL.md 散文改为结构化卡片包（.json + assets），保持 skill 双输出。

卡片语义包 schema v1（草案）：
```
card_package/
├── manifest.json          # 版本、来源卡规格、蒸馏时间、schema 版本号
├── persona.json           # 人设/外貌/语言风格（结构化字段 + 原文引用）
├── worldbook/
│   ├── index.json         # 条目索引：keys/语义向量引用/priority/position/depth
│   └── entries/*.md       # 条目正文（保持原文，可检索）
├── state_machine.json     # 变量定义/默认值/取值范围/更新规则（从卡蒸馏 + 人工确认）
├── routes.json            # 剧情线/开场白路由（first_mes/alternates/disabled 条目）
├── preset_intents.json    # 预设三层意图的结构化表达（非原文话术）
├── regex_semantics.json   # 正则脚本的意图化转写
├── illustrations.json     # 场景→文件映射 + 下载清单
└── assets/                # 插图等二进制资源
```

任务清单：
1. schema v1 定稿（JSON Schema 校验文件一并交付）
2. `generate_package.py`：card_data.json → 卡片语义包；`generate_skill.py` 保留为兼容输出（双输出）
3. 11 张卡全量迁移验证，八等分群友（161 图/五角色/好感度）作为重卡基准
4. **评测集 v1**：每卡 ≥10 组检索标注 + 3 个长会话剧本（各 50 轮，含状态变化点、剧情线切换点）
5. 中文触发增强：条目 keys 的同义词扩展流水线（可由 LLM 批量生成 + 人工抽检）

**验收**：11/11 迁移通过；检索 recall@5 ≥ 90%（P0 标注集 + 评测集 v1）。

### P2（第 6-11 周）：运行时最小闭环（项目的心脏）

**目标**：CLI 可用的单角色引擎，验证体验核心——快、省、稳、有记忆。

模块拆解：
1. **上下文组装器**：`人设 + 当前状态 + 近 N 轮 + 命中世界书条目 + 记忆检索结果 + 摘要`，带 token 预算管理器（超预算时按 priority/recency 降级）
2. **双通道检索**：BM25 + 向量，RRF 融合；条目级命中，超长条目做段落级注入
3. **生成循环**：单次 LLM 调用产出叙事 + 结构化尾部（JSON：state_diff / illustration_trigger / memory_candidates）；解析失败重试（最多 2 次，降级为纯文本并告警）
4. **状态校验回路**：state_diff 合法性（范围/类型）→ 与记忆库矛盾检测（轻量规则 + 可选 NLI）→ 通过才落库
5. **存档**：SQLite（sessions / state / memory / index），随时 save/load，含分支点
6. **记忆 v0**：会话结束触发事实抽取（角色视角："玩家送过怀表"）→ 记忆库 → 下次会话检索注入
7. CLI 交互闭环（菜单/输入/流式输出），**不做 UI**——先用 CLI 把体验核心调对

技术栈建议（P2 起冻结）：

| 组件 | 选型 | 备注 |
|---|---|---|
| 语言 | Python 3.11+ | 复用 distiller 全部资产 |
| 存储 | SQLite + sqlite-vec | 单文件、零运维；量大再换 LanceDB |
| 检索 | jieba + tantivy-py（BM25）+ bge-m3（本地） | bge-m3 需可选 API 模式兜底低配机器 |
| LLM 接入 | OpenAI 兼容统一层 + Anthropic 适配 | 国内（Ark/DeepSeek/DashScope）走 OpenAI 兼容 |
| API 服务 | FastAPI + WebSocket | P2 末尾就加上，P3 的 UI 直接对接 |
| UI | Svelte 或 React + Vite | P3 |
| 打包 | PyInstaller（单包）/ Tauri（壳）/ Docker | P3 |

**验收**：
- 50 轮长会话，单轮上下文稳定 ≤ 4K token（评测脚本断言）
- 状态零漂移：剧本中所有状态变化点被正确落库（脚本对比 diff）
- 跨会话记忆演示：上个存档的关键事实在下个存档被自然提及
- 与酒馆重度配置的成本对照报告（宣传用硬数字）

### P3（第 12-17 周）：体验层及格线

**目标**：从"能用的引擎"到"敢给别人装的软件"。

1. Web UI：流式聊天、存档管理（卡片墙）、**swipe 重roll**、分支树、状态面板、插图画廊
   - swipe/分支是酒馆用户的迁移硬前置，优先级高于一切美化
2. 模型接入向导：检测本地 Ollama → 引导配置国内 API key（Ark/DeepSeek/DashScope）→ OpenAI/Anthropic
   - "部署成本的真痛点不在安装，在 API 配置"——这个向导是转化率关键
3. 一键安装：Windows/macOS 单包 + Docker compose；首次启动零配置即可进入对话（内置一个离线演示卡）
4. 插图管线：命中 → 本地发送/压缩（Web 端直接展示，无需 MEDIA: hack）
5. 兼容性回归：11 张卡在 UI 全流程跑通

**验收**：新用户从下载到第一轮对话 ≤ 5 分钟（含模型配置）；swipe/分支/存档全可用。

### P4（第 18-24 周）：差异化与公测

1. 记忆完整版：冲突消解（玩家 retcon）、遗忘修剪、按角色/世界分区——参考 BRING 的实体抽取与矛盾检测设计
2. 主动性调度器 v1：定时事件（晚安消息）、离线演化（好感度缓变、世界事件入记忆）、主动消息节流阀（防骚扰）
3. 多 agent 群聊 v1（资源允许时）：独立角色上下文 + 裁判调度；重卡基准=八等分群友
4. 公测发布：GitHub + 酒馆社区（迁移漏斗：distiller 引流 → 文档"从酒馆搬家"指南）
5. 北极星验证：公开演示"玩 50 轮 → 放下 → 一个月后回来，角色记得你并主动说了一句话"

## 3. 横切事项（贯穿全程）

- **评测即门禁**：每个 PR 跑检索召回 + 状态一致性回归；评测集随功能同步扩充
- **成本仪表**：每次发布附单轮 token / 端到端延迟基准报告（对酒馆重度配置的对照曲线）
- **内容边界**：预设蒸馏只转"沉浸意图"，不复刻对抗性话术；发布页明确模型政策边界与本地数据隐私声明（数据不出本机是卖点也是合规底线）
- **上游风险**：若 P0 决定 fork OpenCharaAgent，锁定 Apache-2.0 合规（保留版权声明）、按 tag 固定版本、抽象层隔离其 API（单人项目停更风险对冲）

## 4. 风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| 检索漏触发 → "失忆事故"劝退用户 | 高 | 评测集先行（P0）、双通道冗余、置信度低时宁多注入 |
| 瘦上下文导致角色变"薄" | 高 | 摘要质量是 P2 主要打磨项；对照实验（全量 vs 瘦）盲测 |
| 单人周期过长，热情耗尽 | 中 | 每阶段有可发布物（v0.2 工具→CLI→UI→公测）；P2 结束即可内部邀测 |
| OpenChara 上游停更/转向 | 中 | 抽象层隔离；自建路径在 P0 已验证可行 |
| 模型政策变化影响核心体验 | 中 | 模型接入层多供应商；明确宣传"体验依赖所选模型" |
| catbox 等图床失效 | 低 | 迁移时落盘到本地包；下载脚本加镜像占位 |
